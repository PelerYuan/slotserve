# 调度原理

SlotServe 只维护一个 `llama-server` 进程。调度器每隔几秒（以及预约或模型变更后立即）判断此刻*应当*加载哪个模型，并让进程向它靠拢。

## 选择目标模型

1. **有进行中的预约** → 该预约的模型及参数预设；*整卡*预约则不加载任何模型（停止 llama-server）。
2. **下一个预约将在「其模型的预计加载时间 + 60 秒」内开始** → 立即预加载下一个预约的模型。整卡预约会提前 `SLOTSERVE_STOP_TIMEOUT_SECONDS` + 60 秒停止 llama-server。
3. **下一个预约太近，切回默认模型只能用一小会儿**（间隔 < 默认模型加载时间 + 下一个模型加载时间 + 2 × 缓冲）→ 跳过默认模型，直接加载下一个预约的模型。
4. **管理员手动指定了模型（或卸载）** → 按手动设置，直到时间到或下一个预约开始。
5. **其他情况** → 默认模型（未设置默认模型则不加载）。

「模型 + 参数预设」作为一个整体：同一文件换预设也会重启 llama-server。

只有目标与当前模型不同时才会重启进程。提前结束预约会立即触发重新评估。

## 加载时间估算

- 模型成功加载过之后，取其最近 5 次成功加载的平均耗时。
- 在此之前按 `文件大小 ÷ SLOTSERVE_DISK_READ_MBPS + 15 秒` 估算。

机械盘加载很慢，而页缓存只有在空闲内存大于模型大小时才有帮助。把常用模型放在 SSD 上是最有效的改进。

## 谁能调用接口

| 情况 | 预约者 | 其他人 |
| --- | --- | --- |
| 没有进行中的预约 | 可用（当前模型） | 可用（当前模型） |
| 有进行中的预约，模型已就绪 | 可用 | `403 gpu_reserved` |
| 有进行中的预约，模型仍在加载 | `503` + `Retry-After` | `403 gpu_reserved` |
| 有进行中的整卡预约 | `503 gpu_exclusive` | `403 gpu_reserved` |

空闲时段的使用属于尽力而为：预加载下一个预约的模型时可能会被打断。

## 相邻预约

加载只能在前一个预约结束后开始。如果两个相邻预约使用不同模型，后一个预约的开头会用于加载；若使用同一模型则完全不需要重新加载。预约对话框会给出提示。

## 切换时不打断请求

目标模型变化时，SlotServe 先让已在进行的请求跑完（最多 `SLOTSERVE_DRAIN_SECONDS`，默认 30 秒），期间新请求返回 `503 model_switching` 和 `Retry-After`；之后才停止 llama-server 并加载下一个模型。**重新加载模型**仍立即重启。

## 失败处理

- 如果日志显示显存不足，错误信息会直接说明，并建议调小 `-ngl` 或 `-c`。文件比显存还大的模型会在模型列表和预约对话框中标记**超出显存**。

- llama-server 退出，或在 `SLOTSERVE_LOAD_TIMEOUT_SECONDS` 内未就绪时，运行状态标记为**失败**并记录原因，调度器以递增的间隔重试（30 秒 → 10 分钟）。
- **自动回退**：预约的模型在等待下一次重试期间，由默认模型为该预约提供服务，预约人不会无模型可用。总览页会显示提示，预约人和管理员会收到通知；重试成功后切回预约的模型。
- 总览页会显示错误，**运行日志**里能看到 llama-server 自己的输出。
- `-m`、`--host`、`--port`、`--alias` 由 SlotServe 管理，会从用户参数中剔除，写错也不会影响转发。
