    Configuration¶

    SlotServe reads SLOTSERVE_* environment variables, or a .env file in its working directory. Docker Compose loads .env automatically.

    Compose variables¶

    These only exist in docker-compose.yml and describe the host.

    Variable Default Description
    LLAMA_CPP_DIR required Directory containing llama-server; mounted read-only at /opt/llama.cpp
    MODELS_DIR required Directory with .gguf files; mounted at /models
    DATA_DIR ./data SQLite database and logs; mounted at /data
    PORT 8000 Published port
    CUDA_IMAGE nvidia/cuda:12.8.1-runtime-ubuntu24.04 Base image; match the CUDA major version of your llama.cpp build

    llama-server¶

    SlotServe runs SLOTSERVE_LLAMA_SERVER_CMD for llama.cpp models; in Docker that is /opt/llama.cpp/llama-server, the llama-server in LLAMA_CPP_DIR. The health check engine (and the setup checklist item Inference engine) says whether it is found. If not: LLAMA_CPP_DIR must be the directory that contains llama-server itself (usually llama.cpp/build/bin), the file must be executable and built for this machine, and shared builds need their lib*.so files next to it. Without Docker, set SLOTSERVE_LLAMA_SERVER_CMD to the full path.

    SlotServe settings¶

    Admins change every setting except the deployment parameters in Admin → System settings, without a restart: overrides live in the database and win over .env, and Use default removes one. Each change is in the audit log with its old and new value (secrets only as a fingerprint) and can be undone. Level is where the setting appears: basic on the policy cards, advanced in the full list, expert folded away. Settings marked ⚠️ can run commands as root on the host (an engine command, a mounted directory, a forwarder image): changing them is recorded as a sensitive change and announced to all admins (a later version also asks for your password again). The deployment parameters are read at start: change them in .env and restart.

    Per-model launch arguments¶

    Each model has a free-form argument string that is appended to the command. For llama.cpp models:

    <SLOTSERVE_LLAMA_SERVER_CMD> -m <file> --host 127.0.0.1 --port 8081 --alias <name> <your arguments>

    vLLM, SGLang and custom engines build their command the same way; see GPUs, lanes & engines.

    -m, --host, --port and --alias are always set by SlotServe; copies in your arguments are ignored. Useful arguments:

    Goal Arguments
    Offload all layers -ngl 99
    Context size -c 16384
    Parallel requests -np 4 (context is split between slots)
    Flash attention --flash-attn on
    Vision models --mmproj /models/mmproj-model-f16.gguf
    Embeddings --embedding --pooling mean
    KV cache quantization -ctk q8_0 -ctv q8_0

    Run llama-server --help for the full list. After editing the arguments of the loaded model, press Reload model on the overview page.

    Backups and restore¶

    SlotServe writes a backup bundle (database, generated secret key, SSH host keys, manifest) to data/backups/ every day at SLOTSERVE_BACKUP_HOUR, keeps the newest SLOTSERVE_BACKUP_KEEP, and copies each one to SLOTSERVE_BACKUP_TARGET (a mounted path or storage:<id>) when it is set. Admin → Overview → Backups lists them and makes one on demand. A snapshot is also taken before every database upgrade; those are never deleted. slotserve restore <bundle> puts one back (with the server stopped) and the next start shows a reconciliation report.

    Workspaces, kept environments' data, saved images and models are not part of a backup. Details, the off-machine copy and the restore steps: Backups and Restore from a backup.

    First admin and setup code¶

    While no admin account exists, SlotServe prints a one-time setup code in its log at every start:

    docker compose logs slotserve | grep -A4 "No admin account"
docker compose exec slotserve slotserve setup-code     # or ask for it directly

    Open SlotServe: the sign-up form asks for the setup code instead of the invite code, and the account becomes the admin. The code stops working as soon as an admin exists, and installations that already have an admin never ask for it. Everyone else signs up with the invite code (or is created in Admin → Users).

    Requests from other pages¶

    SlotServe refuses changing requests (POST, PUT, PATCH, DELETE) to its own API that do not come from its own pages: an Origin must be SlotServe's own address (the host the browser used, or SLOTSERVE_PUBLIC_URL), Origin: null is always refused, and requests with the session cookie but without Origin must carry the header X-SlotServe: 1 (the web UI sends it). This stops pages on dev environment ports or other sites from acting for a signed-in person. API clients are not affected: /v1 with API keys, /metrics, chat platform callbacks and scripts without the session cookie.

    Behind a reverse proxy, pass the original host (proxy_set_header Host $host; for nginx) or set SLOTSERVE_PUBLIC_URL; otherwise changes made in the web UI are refused with "did not come from a SlotServe page".

    Admin command line¶

    Most account tasks are done in Admin → Users. The command line is for when no admin can sign in:

    docker compose exec slotserve slotserve setup-code               # code for creating the first admin
docker compose exec slotserve slotserve reset-password <username>
docker compose exec slotserve slotserve set-admin <username>
docker compose exec slotserve slotserve set-admin <username> --revoke
docker compose exec slotserve slotserve doctor                   # run the health checks (exit code 1 on an error)
docker compose run --rm --no-deps slotserve slotserve restore <bundle>   # with the server stopped

    See Operations for when to use which.
